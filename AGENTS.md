# Agent guidelines

Guidance for humans and coding agents working in this repository. See [README.md](README.md) for the overall purpose and the versioning scheme.

## Modules

A module is a directory `deployments/<app>/<site>` (for example `deployments/opencti/ps6`). Every module is tested, tagged and updated by Renovate independently, so keep a change scoped to a single module whenever possible.

A module contains:

- `main.tf`, `variables.tf`, `versions.tf` and, when it exposes values, `outputs.tf`. Extra files (`data.tf`, `locals.tf`) are fine.
- `README.md` describing what is deployed, the models it needs and the outbound access it requires. The Terraform inputs/outputs section is generated by the docs workflow, do not edit it by hand.
- `tests/main.tftest.hcl` and a `tests/setup` module that creates the model(s) the tests plan against. Tests use `command = plan` and assert on outputs.

Every `.tf` file starts with the Canonical copyright header:

```hcl
# Copyright <year> Canonical Ltd.
# See LICENSE file for licensing details.
```

Modules must be self-contained: do not reference files from another module or from outside `deployments/<app>/<site>` through relative paths. Change detection, tagging and Renovate grouping all assume that a module only depends on its own directory.

## Pinning charms and modules

- Every charm `revision = N` line in `main.tf` must be immediately preceded by a Renovate comment, otherwise Renovate silently stops updating it (enforced by `scripts/check-renovate-comments.py`):

  ```hcl
  channel = "latest/stable"
  # renovate: charm="ingress-configurator" track="latest" risk="stable" base="24.04" arch="amd64"
  revision = 111
  ```

- Pin remote Terraform modules to a tag with `?ref=<tag>&depth=1`, using the `rev<N>` or `<charm>-rev<N>` tags published by charm CI. If a tag family does not match the versioning regexes in `renovate.json`, add a `packageRules` entry for it.

## Adding a new module

A new module must be registered in all of the following places, in the same PR:

1. `scripts/changed_modules.sh`: add it to exactly one test group (`k8s_modules` or `lxd_mixed_modules`) depending on the controller its tests need. The test workflow fails if a module is missing.
2. `renovate.json`: add a `packageRules` entry at the end of the list so its updates are grouped in a single PR:

   ```json
   {
     "matchFileNames": ["deployments/<app>/<site>/**"],
     "groupName": "<app>-<site>",
     "separateMajorMinor": false
   }
   ```

3. `.github/workflows/generate_terraform_docs.yaml`: add the directory to `terraform-directory`.

Removing or renaming a module requires the same edits in reverse.

## Checks

Run these before pushing (also available through `just` and the [prek](https://github.com/j178/prek) hooks in `.pre-commit-config.yaml`):

- `terraform fmt -recursive` and `scripts/terraform-lint.sh` (tflint)
- `scripts/check-renovate-comments.py`
- `npx --yes --package renovate -- renovate-config-validator renovate.json` when editing `renovate.json`
- `scripts/changed_modules.sh origin/main HEAD` to see which modules CI will test

## CI and releases

- `test_terraform_modules.yaml` only tests the modules changed by a PR (all modules when workflows or `scripts/changed_modules.sh` change). The `all-tests-passed` job is the required check.
- On merge to `main`, `tag_on_merge.yaml` tags each changed module as `<app>-<site>/<YYYY.MM.DD>.<n>` and creates a release for it.
